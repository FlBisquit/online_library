## Общие правила (CONVENTIONS.md / начало каждой сессии)

Стек: Django 6 + DRF + SimpleJWT, MySQL/MariaDB, React (Vite).

1. Перед правкой прочитать затронутые файлы целиком. Небольшие шаги, коммиты
   на английском.
2. Тесты на MySQL, не на SQLite. После шага: `manage.py check`,
   `makemigrations --check`, `test`; для фронта `npm run build`.
3. Схема БД меняется только миграциями. Секреты не коммитить, в репозитории
   только `.env.example`.
4. Любая операция, меняющая состояние, идёт в `transaction.atomic()`; первым
   запросом блокируется ресурс через `select_for_update()`, затем проверки,
   затем запись. Порядок блокировок: Book, BookCopy (по id), Reservation (по
   queue_date, id), Issue.
5. `user_id` берётся только из `request.user`. Исключение: сотрудник действует
   от имени читателя.
6. Конфликт — 409, нет прав — 403, нет объекта — 404, неверный ввод — 400.
   На ожидаемые ситуации 500 быть не должно.
7. К каждому исправлению — тест, который падал бы до него.
8. В конце — запись в `docs/AI_LOG.md`.

## Промпт 1. Конфигурация и настройки безопасности

**Задача:** исправить `backend/config/settings.py`, `backend/requirements.txt`,
`.env.example`.

**Проблемы:**
- `BASE_DIR` указывает на корень репозитория, поэтому `backend/.env`
  игнорируется, а значения молча заменяются дефолтами.
- Небезопасные дефолты `SECRET_KEY`, `DEBUG=True`.
- `ACCESS_TOKEN_LIFETIME` 60 минут вместо 15.
- `CSRF_TRUSTED_ORIGINS` не читается из окружения.
- `django>=4.2` не подходит для миграций с `CheckConstraint(condition=...)`.

**Что сделать:**
1. `BASE_DIR` = папка `backend`; `read_env` читает `BASE_DIR / '.env'`.
2. `SECRET_KEY` и `DATABASE_URL` обязательны, при отсутствии —
   `ImproperlyConfigured`. `DEBUG=False` по умолчанию. `ALLOWED_HOSTS`,
   `CORS_ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS` из окружения.
3. SIMPLE_JWT: access 15 минут, refresh 7 дней, ротация и blacklist после
   ротации. Throttling: anon 60/min и отдельный scope для `/api/token/` (10/min).
4. `requirements.txt`: `Django>=5.1,<7` и минимальные версии остальных пакетов.
5. `frontend/.env.example` с `VITE_API_BASE_URL=/api`.

**Проверка:** неверный пароль в `DATABASE_URL` ломает `migrate` (файл
читается); без `SECRET_KEY` приложение не стартует; тест `exp - iat = 900`;
`manage.py test` проходит.

## Промпт 2. Регистрация, роли, блокировка

**Задача:** починить регистрацию, роли и вход (`serializers.py`, `views.py`,
`models.py`, `urls.py`).

**Проблемы:** `POST /api/readers/` создаёт пользователя без группы `reader`;
пароль не валидируется и необязателен; заблокированный читатель получает
токены; роль определяется запросом на каждую проверку.

**Что сделать:**
1. Регистрация на `POST /api/auth/register/` (AllowAny): email, password,
   full_name, phone. Пароль обязателен и проходит `validate_password`. Роль
   всегда `reader`; клиент не передаёт groups, status, is_staff. Дубликат
   email — 409. Старый публичный `POST /api/readers/` удалить.
2. `Reader.is_active` — свойство `status == ACTIVE`.
3. Кэшировать роли на время запроса.
4. `GET /api/auth/me/`: текущий пользователь и роли.
5. `POST /api/token/blacklist/` делает refresh непригодным (401); невалидный
   refresh — 400/401, не 500.

**Тесты (падают до исправления):** группа `reader`; слабый пароль 400; нельзя
передать groups/status; BLOCKED не получает токен, старый access отклоняется;
`/auth/me/` возвращает роли; logout даёт 401 на refresh.

## Промпт 3. Каркас фронтенда: авторизация, API-клиент, рендер вкладок

**Задача:** `App.jsx`, `AuthContext.jsx`, `api/client.js`, регистрация.

**Проблемы:** `setInitialized(true)` нигде не вызывается — вечная «Загрузка...»,
сессия не восстанавливается; `App.jsx` рендерит `{activeTab.component}` вместо
элемента; `client.js` игнорирует `params`, нет refresh по 401, ошибки DRF не
разбираются; нет страницы регистрации.

**Что сделать:**
1. `client.js`: query string из `params` (пропуская пустые); при 401 один
   вызов `POST /token/refresh/` (общий promise для параллельных запросов),
   сохранение новой пары, повтор запроса; при неудаче — очистка токенов и
   `onAuthLost`; разбор ошибок DRF; метод `download(path)` для CSV.
2. `AuthContext`: при монтировании загрузить `/auth/me/`, всегда вызвать
   `setInitialized(true)`; logout вызывает `/token/blacklist/`.
3. `App.jsx`: `<ActiveComponent />`, вкладки по ролям; admin видит и панель
   библиотекаря; при отсутствии ролей — понятное сообщение.
4. `RegisterPage` и переключатель «Вход / Регистрация»; после регистрации — вход.
5. Общие `<Loading/>`, `<EmptyState/>`, `<ErrorMessage/>`.

**Проверка:** `npm run build`; сессия переживает перезагрузку; токен
прозрачно обновляется; после выхода refresh даёт 401; нет бесконечных повторов.

## Промпт 5. Очередь и бронирование (главное правило варианта)

**Правило:** если свободных экземпляров нет, читатель встаёт в очередь; при
возврате экземпляр резервируется за первым в очереди.

**Баги:**
a) `GET /api/books/id/queue/` — 500 (`to_representation` у `ListSerializer`);
очередь с данными всех читателей видна любому.
b) `POST /api/books/9999/queue/` — 500 вместо 404.
c) `join_queue` без транзакции и блокировки: 10 параллельных запросов дали
1×201, 5×409, 4×500; нужно 1×201 и 9×409.
d) `UniqueConstraint(reader, book, status)` ломает повторный цикл join/cancel.
e) Встать в очередь можно при наличии свободного экземпляра.

**Что сделать:**
1. Единый порядок блокировок Book → BookCopy → Reservation → Issue; в
   `return_issue` сначала прочитать `book_id`, залочить Book, затем Issue.
2. Заменить unique на `active_slot` (1 для PENDING/ACTIVE, NULL иначе) с
   `UniqueConstraint(reader, book, active_slot)`; миграция схемы и данных.
3. Глобальный обработчик: `IntegrityError` → 409 (`config/exceptions.py`).
4. Позиция по PENDING и ACTIVE, порядок `(queue_date, id)`; ответ с
   `position` и `total`.
5. `Reservation.copy` (FK, null), заполняется в `_promote_next`; отмена
   ACTIVE освобождает именно этот экземпляр.
6. Читатель отменяет только свою бронь, сотрудник любую; чужая — 403.

**Тесты (MySQL):** 10 параллельных join → 1×201; join при свободном
экземпляре → 409; 5 циклов join/cancel; 404 на несуществующую книгу; читатель
не видит чужую очередь; очередь из двух, возврат, RESERVED первому, выдача
второму 409, первому 201 и FULFILLED.

## Промпт 6. Истечение резервов

**Проблемы:** `expire_reservations()` нигде не вызывается;
`select_for_update` вне транзакции; `issue_copy` не проверяет `expires_at`;
`_promote_next` освобождает максимум один просроченный резерв.

**Что сделать:**
1. `expire_reservations(book_id)` внутри `transaction.atomic` с тем же порядком
   блокировок; цикл: ACTIVE с `expires_at < now` → EXPIRED
   (`active_slot=NULL`), экземпляр AVAILABLE, `_promote_next`; повторять до
   исчерпания. Запись в `ActionLog` (`user=NULL`, `reservation.expire`).
2. Вызывать лениво: `join_queue`, `issue_copy`, `return_issue`,
   `cancel_reservation`, выдача списка экземпляров и карточки книги; плюс
   команда `expire_reservations` для cron.
3. `issue_copy` по просроченному резерву не выдаёт (409 или продвижение).
4. `ActionLog.user` nullable (`SET_NULL`); миграция.

**Тесты:** время через `mock.patch('django.utils.timezone.now')`; следующий в
очереди получает экземпляр; цепочка из 3 за один вызов; выдача по
просроченному резерву — 409; повторный вызов идемпотентен.

## Промпт 7. Статусы: карта переходов, OVERDUE, LOST

**Проблемы:** проверки переходов разбросаны; OVERDUE и LOST не выставляются;
нет «отметить потерянной»; читатель сам возвращает книгу; `ActionLog` не
хранит старый и новый статус.

**Что сделать:**
1. `library/transitions.py`. Issue: ISSUED → RETURNED/OVERDUE/LOST;
   OVERDUE → RETURNED/LOST; LOST → RETURNED; RETURNED без переходов.
   Reservation: PENDING → ACTIVE/CANCELLED; ACTIVE →
   FULFILLED/CANCELLED/EXPIRED. BookCopy по аналогии, ISSUED и RESERVED
   вручную не ставятся. `change_status(obj, new_status, user)` проверяет
   переход, сохраняет и пишет `ActionLog` в одной транзакции; недопустимый
   переход — 409.
2. Возврат и LOST только librarian/admin; отмена брони — своя у читателя,
   любая у сотрудника.
3. `mark_overdue()` (`UPDATE ... WHERE status=ISSUED AND due_at < now`),
   лениво и командой `manage.py mark_overdue`.
4. `POST /api/issues/id/mark-lost/`.
5. `ActionLog`: `entity_type`, `entity_id`, `old_status`, `new_status`,
   индексы; миграция.

**Тесты:** перебор всех пар статусов (`subTest`); читатель не возвращает
книгу (403); `mark_overdue`; откат статуса и записи при исключении.

## Промпт 10. Админка: каталог и пользователи

**Проблемы:** `GET /api/readers/` — 405 из-за дублирующего маршрута;

**Что сделать:**

   `PATCH /api/users/id/` меняет только role и status; нельзя понизить или

удаление книги с выдачами — 409.

## Промпт 12. Демо-данные

**Проблемы:** повторный запуск падает `IntegrityError`; на каждую книгу свой
жанр; у OVERDUE и LOST экземпляр остаётся AVAILABLE; нет очереди для демонстрации,
обложек; одна бронь.

**Что сделать:**
1. Идемпотентность (`update_or_create` по email, isbn, inventory_number);
   `--reset` в одной транзакции.
2. Пользователи: admin, librarian, reader0..7 с паролями из README и один
   BLOCKED-читатель.
3. 8–10 авторов, 8 жанров, не меньше 24 книг (1–3 автора, 1–2 жанра, обложка,
   1–4 экземпляра).
4. Не меньше 30 выдач (RETURNED, ISSUED, OVERDUE, LOST) через `change_status`,
   даты за последние 60 дней.
5. Сценарий очереди: книга X — все экземпляры выданы, 3 читателя PENDING;
   книга Y — ACTIVE-резерв для reader0 и RESERVED экземпляр; CANCELLED и
   EXPIRED брони за месяц.
